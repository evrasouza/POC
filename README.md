# BRP Public Websites Playwright Framework

This project is a TypeScript Playwright automation framework for BRP public websites.

The framework provides a shared multi-brand and multi-locale architecture for automated testing across:

- Can-Am Off-Road
- Can-Am On-Road
- Sea-Doo
- Ski-Doo
- Lynx

The goal is to reuse the same test scenarios across brands and locales whenever the user experience is shared, while keeping brand-specific differences isolated in configuration or reusable components.

The framework is designed to grow into coverage for navigation, product discovery, forms, lead generation, dealer flows, localization, analytics, APIs, and other public website functionality.

## Architecture

Tests describe behavior while configuration determines which website and locale are tested.

```text
Test
  ↓
Page Object
  ↓
Reusable Components
  ↓
Site Context
  ↓
Brand + Locale Configuration
  ↓
URL Builder
  ↓
BRP Website
```

Tests should not contain brand-specific URLs or duplicate scenarios unless the user experience genuinely differs between brands.

## Brand Configuration

Brands live in `config/brands.ts`.

Each brand contains the information required to construct its URLs.

Example:

```ts
{
  id: 'canam-offroad',
  displayName: 'Can-Am Off-Road',
  origin: 'https://can-am.brp.com',
  productLinePath: 'off-road',
}
```

Can-Am Off-Road and Can-Am On-Road use product-line paths.

Sea-Doo, Ski-Doo, and Lynx do not require the same product-line URL structure.

These differences remain in configuration instead of being duplicated throughout tests.

## Locale Configuration

The locale is dynamic.

Configuration priority is:

```text
Command-line parameters
        ↓
Environment variables
        ↓
Default values
```

Defaults:

```text
brand = canam-offroad
country = ca
language = en
```

Example locales include:

```text
ca/en
ca/fr
us/en
us/es
br/pt
de/de
fr/fr
no/no
fi/fi
se/sv
```

The framework does not assume that every brand supports every locale.

## URL Generation

URLs are generated by `utils/url-builder.ts`.

Example:

```ts
buildUrl({
  brand: 'canam-offroad',
  country: 'ca',
  language: 'en',
  path: '/',
});
```

Result:

```text
https://can-am.brp.com/off-road/ca/en/
```

Sea-Doo example:

```ts
buildUrl({
  brand: 'seadoo',
  country: 'ca',
  language: 'en',
  path: '/',
});
```

Result:

```text
https://sea-doo.brp.com/ca/en/
```

Internal paths are also generated dynamically:

```ts
buildUrl({
  brand: 'canam-offroad',
  country: 'ca',
  language: 'en',
  path: '/models/sxs',
});
```

The URL builder also normalizes paths and locale casing.

## Running Tests

Run all tests using the default configuration:

```bash
npm test
```

Run against a specific brand and locale:

```bash
npm test -- --brand=seadoo --country=ca --language=en
```

Run a specific test file:

```bash
npm test tests/navigation/header.spec.ts --brand=seadoo --country=ca --language=en
```

### Smoke Tests

```bash
npm run test:smoke -- --brand=canam-offroad --country=ca --language=en
```

### Unit Tests

```bash
npm run test:unit
```

### Headed Mode

Use headed mode to watch the browser execute the tests:

```bash
npm run test:headed -- tests/navigation/header.spec.ts --brand=seadoo --country=ca --language=en
```

### Debug Mode

Use Playwright Inspector to execute and inspect tests step by step:

```bash
npm run test:debug -- tests/navigation/header.spec.ts --brand=seadoo --country=ca --language=en
```

Debug mode is useful for:

- stepping through Playwright actions;
- inspecting locators;
- checking element visibility;
- investigating failed interactions;
- observing navigation behavior.

### Playwright UI Mode

```bash
npm run test:ui
```

### HTML Report

```bash
npm run report
```

## URL Builder Unit Tests

`tests/unit/url-builder.spec.ts` protects the URL-generation layer.

Current coverage includes:

- Can-Am Off-Road homepage URL;
- Can-Am On-Road homepage URL;
- Sea-Doo homepage URL;
- Lynx homepage URL;
- internal paths;
- path normalization;
- uppercase locale normalization.

These tests run without requiring browser navigation to the public websites.

## Homepage Smoke Test

`tests/smoke/homepage.spec.ts` validates that the configured public website can be loaded successfully.

The test verifies:

1. The selected brand and locale URL can be generated.
2. Navigation returns an HTTP response.
3. The response is successful.
4. The document body is visible.
5. The browser remains on the expected hostname.
6. The page has a non-empty title.

The smoke test intentionally avoids marketing-copy assertions so it can be reused across brands and languages.

## Shared Header Navigation Tests

`tests/navigation/header.spec.ts` validates shared global navigation behavior.

Current coverage verifies that:

1. The global header is visible.
2. The main navigation is visible.
3. The navigation contains links.
4. An internal navigation link can be selected.
5. Clicking the link results in navigation.
6. Navigation remains within the expected website hostname.

The same tests are reused across supported BRP brands.

## Handling Cookies and Promotional Overlays

Public BRP websites may display cookie consent widgets or promotional modals that prevent normal page interaction.

Reusable components handle these conditions before functional interactions:

```text
CookieBannerComponent
PromotionalModalComponent
```

`HomePage.prepareForInteraction()` prepares the page before navigation scenarios by dismissing supported overlays when they are present.

This behavior remains separate from `goto()` so cookie and promotional-modal behavior can still be tested independently in future scenarios.

## Reusable Components

Shared website regions should be represented by reusable components.

Current examples:

```text
HeaderComponent
FooterComponent
CookieBannerComponent
PromotionalModalComponent
```

The `HeaderComponent`, for example, separates the complete header from the main navigation:

```text
Header
  ├── Header content
  └── Main Navigation
        └── Navigation Links
```

Tests interact with the component instead of duplicating DOM locators inside specs.

## Adding Another Brand

Add a new entry to `config/brands.ts`:

```ts
'example-brand': {
  id: 'example-brand',
  displayName: 'Example Brand',
  origin: 'https://example.brp.com',
  productLinePath: 'optional-product-line',
}
```

Then add the new ID to `BrandId` in `types/site.types.ts`.

Shared tests should not require changes.

## Adding Another Locale

No source change should be required for a standard country/language URL.

Example:

```bash
npm test -- --brand=canam-offroad --country=br --language=pt
```

If a future website has a non-standard locale format, that knowledge should remain in the configuration or URL-builder layer.

## Creating a New Page Object

Create page classes inside `pages/` and extend `BasePage`.

Example:

```ts
import { BasePage } from './base.page.js';

export class ProductListingPage extends BasePage {
  async gotoListing(): Promise<void> {
    await this.goto('/vehicles');
  }
}
```

Add the page object to `fixtures/test.fixture.ts` when convenient fixture access is required.

## Creating a Reusable Component

Shared website regions belong in `components/`.

Example:

```ts
export class NavigationComponent {
  constructor(private readonly page: Page) {}
}
```

Components should represent reusable functionality such as:

- header;
- footer;
- cookie consent;
- promotional modals;
- navigation;
- dealer locator;
- lead forms.

## Creating a New Test

Tests should describe behavior.

Configuration determines where that behavior runs.

Example:

```ts
import { test, expect } from '../../fixtures/test.fixture.js';

test('homepage loads', async ({ homePage }) => {
  const response = await homePage.goto();

  expect(response?.ok()).toBe(true);
});
```

Avoid duplicating tests by brand or locale unless the actual user experience requires different behavior.
